# BallerWatch V2 — implementation and operations

Current product release: **8.10.2** (V2 introduced in 8.10.0). V2 is an additive frontend capability; it does not replace V1 or change the backend data model.

## Architecture and secure shared data

The project remains dependency-free plain JavaScript in production. Both HTML documents load the **same** `frontend/web/app.js` exactly once. That controller owns session restoration, critical public calendar/next-match rendering, optional scouting, calendar selection, card trains, standings, team history, venue sharing, roster access, account/admin dialogs, AI, Inbox, notifications, Web Push, badge synchronization, update detection and polling. V2 changes the layout around these existing DOM contracts and reuses the existing protected operations.

`lib/client.js` remains the sole API/session transport. Both versions call the same Cloudflare Worker endpoints, which mediate the same canonical AES-GCM-encrypted `runtime-state` branch. V2 introduces no backend endpoint, state branch, dataset, watcher, indexing job or Calendar synchronization job. No browser request reads encrypted state directly. Authentication and account-level Inbox state intentionally remain shared.

The existing capability token contract is unchanged. No new token copy/store is introduced. Private roster responses and scouting reports stay in memory; private responses are never cached by the frontend worker. The existing short-lived, tab-scoped **public-only** calendar fallback is reused under a V2-specific key. Music, question history, AI context and intro experience keys are V2-namespaced; V1's corresponding preference values are preserved.

There is one set of polling timers per page. The V2 navigation and animation code create no data polling timers or API clients. Separate open V1/V2 tabs retain the existing per-tab behavior; no new cross-tab polling coordinator is introduced.

## Layout and navigation

- **Matchday:** real next-match card with pickup/league type, RSVP capacity/roster, weather, venue, field-only sharing, directions and existing authorized match actions. On phones, the next-match card precedes the decorative editorial panel.
- **Schedule:** existing expandable calendar and same-day game picker. Selecting a game returns to its Matchday card. Empty days retain calendar expansion behavior.
- **Club:** the existing swipeable tracked-team standings train, form and opponent-history/scouting dialogs.
- **Ask BallerWatch:** opens the shared AI dialog. Inbox and account/settings remain available through the header; phones also have an Inbox navigation action.
- **Experience:** Replay the moment, the V1 link, install help and a V2-only frontend-cache control.

Desktop has a left navigation rail; phones have safe-area-aware bottom navigation. Essential navigation never depends on the browser Back button.

## Soccer timeline and tuning

`scene-config.mjs` is the central choreography/asset registry. Its pure `scenePose(progress)` function maps clamped progress 0–1 to all visible poses. The native page scroll drives a sticky full-screen SVG scene; there is no autoplay, physics engine, video, wheel interception or scroll trap. One requested animation frame handles each scroll/resize update, changing SVG transforms and opacity without rerendering application data. Reverse scrolling computes the same poses in reverse.

| Progress | Action / default configuration |
| --- | --- |
| 0–0.15 | Setup and backswing; ball stays still |
| 0.15–0.30 | Shooting leg reaches contact at `SCENE.contact = 0.30` |
| 0.30–0.84 | Ball follows the configured quadratic Bézier, rotates and recedes |
| 0.60–0.80 | `diveStart` to `diveEnd`: keeper reaches toward the incoming shot |
| 0.84–0.92 | Upper-corner arrival and lightweight reversible net pulse |
| 0.92–1.00 | Scene fades while the already-loading real app scrolls into place |

The default ball controls in the 1440 × 900 world are `start (477, 741)`, `control (875, 125)`, and `corner (1260, 390)`. Portrait framing follows the action by translating the world; landscape/desktop retain a wider stadium view. The camera and shot are deterministic and reverse without state resets.

To adjust:

1. **Scroll duration:** change `SCENE.scrollScreens` (default 3.2 screens of travel plus the one-screen sticky stage). The CSS reads the same value and uses stable `svh` sizing.
2. **Ball trajectory:** edit `SCENE.ball.start`, `.control`, `.corner`, `contact` and `flightEnd`; keep the toe-contact and upper-corner positions aligned with the SVG.
3. **Goalkeeper timing:** edit `diveStart` / `diveEnd`; tune `SCENE.keeper` origin, travel and rotation if changing the goal geometry. The near-miss regression checks that the ball clears the outstretched glove.
4. **Replace assets:** the original stadium/crowd/lighting/field/foreground layers are in `v2/assets/stadium.svg`. Player, shooting leg, keeper, ball, goal/net, impact particles and transition/flash layers have stable `scene-*` IDs in `v2/index.html`. Retain the IDs and coordinate system or update `timeline.js` with the replacement geometry. Update `SCENE.stadiumAsset`, the SVG image reference, CSS backdrop and worker shell if replacing the stadium filename.
5. **Replay:** choose **Replay the moment** below Matchday. It returns to the scene without reloading or restarting data retrieval. With reduced motion, replay displays an explanatory message and preserves immediate app access.

All vector artwork is original to this change; no player, club, stadium, game or broadcaster imagery is used. Install PNGs are resized versions of the existing project-owned icon. There are no hotlinked visual assets or encoded raster assets in source.

## Intro resilience and accessibility

Skip immediately collapses the scene, reveals the app, preserves the existing data request/session and focuses the Matchday heading without a reload/history mutation. `ballerwatch:v2:intro-seen` is written only when the sequence finishes or is skipped; scroll progress is never persisted. The long sequence is offered once per tab/installed-app session and can be replayed explicitly.

Reduced motion bypasses the long scene and displays a short static welcome above the functional app. The animation module loads independently of navigation and shared data initialization. Asset errors, module failures and a 2.5-second first-paint watchdog fail open to the app. If the entire V2 navigation module fails, the watchdog reveals all content panels so the shared app remains usable.

Controls have accessible labels, visible keyboard focus and at least 44px targets. Decorative SVG content is hidden from assistive technology. Skip is a real keyboard/touch button and a skip-to-matchday link is first in the document. No essential feature requires the cinematic.

## iPhone, audio and background behavior

V2 uses `viewport-fit=cover`, dark theme/background and Apple standalone metadata. Fixed controls, page padding, dialogs and landscape layouts account for safe-area insets. The V2 grid has environment-backed left/right safe-area padding for landscape navigation and header, with asymmetric Chromium/WebKit regressions. The scene uses `100svh` with a `100vh` fallback; dialogs use `100dvh` to fit dynamic browser chrome. Inputs remain at least 16px, readable text can scale, and native vertical scrolling remains available. Existing horizontal match/standings gestures are retained.

The existing original synthesized stadium soundtrack remains opt-in and gesture-gated, with V2's music key. No audio autoplays before interaction. Existing visibility handling suspends audio; the timeline cancels pending frames in the background and removes page listeners on exit. After the reveal, scrolling further into the app does not keep recomputing the completed scene. Replay restores the necessary listeners, including after back/forward cache restoration.

Automated iPhone viewport, touch, standalone, portrait/landscape and WebKit checks are required. Physical iPhone Safari installation, hardware audio, real push delivery and VoiceOver remain manual device verification; emulation cannot certify them. Tests never send real notifications or mutate Calendar/RSVP.

## Service workers, offline data and updates

V2 registers `v2/sw.js` with scope `./`, which imports the shared `../sw.js` lifecycle. That implementation derives the experience from the **registration's script URL**. V1 retains its existing root registration. Push clicks and icons resolve to the installed experience; V1 does not focus/route an existing V2 window as a V1 launch.

| State/cache | V1 | V2 |
| --- | --- | --- |
| Versioned shell | `ballerwatch-v8-10-0-shell` | `ballerwatch-v2-v8-10-0-shell` |
| Existing derived device badge/category/RSVP state | `ballerwatch-device-state-v1` | `ballerwatch-v2-device-state-v1` |
| Tab-scoped public calendar fallback | existing V1 key | `ballerwatch:v2:public-calendar` |

A worker deletes only its own obsolete shell caches. It does not delete the other app's caches, arbitrary origin caches or either device-state cache. Remote API requests bypass frontend caching. Failed HTTP responses are not cached, missing JavaScript never receives HTML as an offline fallback, and navigation fallbacks come only from that registration's own shell. The V1 parent worker cannot answer an uncontrolled V2 navigation with V1 HTML.

The first worker claim (including V1→V2 scope handoff) does not cause a reload. A later update retains the established refresh behavior. Both shells precache every required document/module/style/icon; older query-versioned assets remain available in each installed shell until its replacement has installed successfully. Worker/Pages release readiness and controller-change handling avoid repeatedly refreshing an incomplete update.

Offline startup provides the cached interface. A prior public schedule in that tab restores with Last synced status; a cold offline launch without one shows a usable reconnecting/empty state. Authentication/private operations still require connectivity.

**Clear only V2 frontend caches:** use **V2 offline storage → Clear V2 frontend cache** below Matchday. It deletes only names matching `^ballerwatch-v2-.*-shell$`. It leaves V1, account tokens, device notification state and encrypted backend state intact. Reconnect before relying on the next offline startup. Do not clear all site data or unregister the root worker.

## Validation and established deployment

Run from repository root:

```bash
node scripts/check-style.mjs
node --test
node scripts/build-web.mjs
node backend/infra/validate-versions.mjs
node scripts/privacy-audit.mjs
node tests/frontend/live-readonly-smoke.mjs
```

Check every JS/MJS file with `node --check`; copy the existing Apps Script `Code.gs` to a temporary `.mjs` and syntax-check it as in CI. Bundle the unchanged Worker using:

```bash
cd backend/infra/web-worker
npx --yes wrangler@4.145.0 deploy --dry-run --outdir /tmp/ballerwatch-worker
```

Browser validation uses a pinned test-only dependency outside the repository:

```bash
npm install --prefix /tmp/ballerwatch-browser --no-save playwright@1.56.1
node /tmp/ballerwatch-browser/node_modules/playwright/cli.js install --with-deps chromium webkit
BALLERWATCH_PLAYWRIGHT_MODULE=/tmp/ballerwatch-browser/node_modules/playwright \
BALLERWATCH_WEB_ROOT=/tmp/ballerwatch-web-build \
node tests/frontend/browser-smoke.mjs
```

The local restricted runner may use `BALLERWATCH_CHROMIUM_SHELL=1`: this mocks only the headless shell's unavailable native worker badge bridge. CI uses the full Chromium binary with the unmodified service worker and WebKit. Pure cache/choreography tests run in both environments.

The suite covers critical reads during the intro, exact reverse poses, dive/goal reveal, native touch scroll, Skip without navigation, refresh, tabs, AI/Inbox opening, portrait/landscape/dynamic resizing, reduced motion/standalone, asset/script failure, synthetic sign-in and shared restoration, authorized roster access, unchanged V1 preference sentinels, optional data failure, last-synced restore, two worker scopes, both offline routes and safe V2 cache clearing.

Release flow is the existing dedicated release branch → green Validate code → PR → checked squash merge into `main` → **Promote production release** → published release/`production` → **Deploy BallerWatch Worker** with encryption audit/live readiness → **Deploy GitHub Pages app** from `production`. The new version-pinned handoff follows the repository's existing `complete-*` pattern, checks the validated current main SHA/ledger and runs read-only production API smoke checks before dispatching the existing promotion workflow. It does not deploy independently or bypass required checks.

Read-only post-deployment verification must check both live HTML documents, V2 direct refresh, all critical static assets/manifests, separate worker registration/launch paths, API readiness and production data through the existing backend. Never use account, push, RSVP or Calendar mutations for live verification.

## Rollback

Do not force-push or reset `production`. Use a new checked release and the same promotion process.

To roll back **only V2**, restore `frontend/web/v2/` to a known-good V2 commit on a new fix/release branch, retain the current V1 files and shared controller, run both suites, bump the product PATCH and both shell cache versions, and promote normally. For the first V2 release, a reversible disabled-V2 page can link to the unchanged V1 root while keeping the V2 manifest/start URL and narrow worker available; avoid deleting the directory or making an installed V2 silently launch V1. Validate every remaining precache entry before promotion.

If a future rollback changes shared modules or root worker behavior, validate V1 and V2 together and retain backwards-compatible contracts. Never roll back, reset or copy canonical runtime-state. A whole-release rollback should likewise be a new forward commit restoring selected source; it is not permission to rewrite production history.
