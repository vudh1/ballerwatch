# BallerWatch Beta and cinematic app

**Production:** https://vudh1.github.io/ballerwatch/ — always built from the explicitly promoted `production` branch.

**Beta:** https://vudh1.github.io/ballerwatch/beta/ — the complete cinematic app built from the last successfully validated `main` commit. Main push validation automatically triggers Pages preview publication, without changing `production`, release tags, the Worker deployment or encrypted runtime-state.

The former `/v2/` URL now redirects to `/beta/`, retaining query and fragment. Legacy V2 install links remain supported. An older installed worker may first need an online refresh before it starts using the new route. Neither environment uses a visitor sign-in for RSVP roster viewing or local match edits.

## Deployment boundaries

`.github/workflows/pages.yml` checks out `production` and `main` separately. On a successful main-branch Validate code push run, it pins the exact validated main SHA. On an explicit Pages dispatch (including a production promotion), it selects an already validated ancestor of current main. `scripts/build-pages.mjs` builds an output containing production at `/ballerwatch/` and a full separate copy of validated main below `/ballerwatch/beta/`. The only modification outside beta is the retired `/v2/` compatibility redirect. GitHub Pages deploys that composed output. A failed or stale validation cannot publish an unvalidated beta.

The beta manifest has a distinct ID/start URL/scope. The beta worker is scoped only to `/ballerwatch/beta/`, uses a validated-commit-specific cache name, and never deletes the root worker's shell or device caches. RSVP names, followed teams, notification choices, cached cards and match edits use beta-specific device keys; production retains its original keys. Visiting beta cannot overwrite match corrections made in production on the same device. The beta page identifies itself as BETA.

**Backend limitation:** Beta previews the current `main` *frontend* against the existing production Cloudflare API and shared public fixture snapshot. A future beta-only backend endpoint or schema change would require its own isolated Worker deployment before being testable; it must not be silently deployed as production.

## Drogon TV channel guide recommendations

The **Watching** match card consults broadcast assignments already published in the weekly ESPN sports index, with a daily near-term TV refresh. BallerWatch stores a sanitized list of 146 channel names copied from the user-provided Drogon TV sidebar on October 25, 2026 (138 ordinary listings and eight marked TEST). This is a static snapshot, not live provider inventory or an entitlement check. Names, including overseas networks, remain catalogued for future exact matches; test channels cannot be recommended. Account details, stream IDs, access links and full HTML are not stored.

The scheduled Node indexer computes `drogonChannels` for each game when an ESPN-reported U.S. broadcaster has an explicit, unambiguous match in the channel catalogue. Examples include ESPN2 → ESPN 2, FS1 → Fox Sports 1 and beIN SPORTS → BeIN Sports. Ambiguous labels (FOX Sports/NBC Sports), unrelated ESPN+ or Peacock services, international networks lacking published rights data and unknown event assignments are **not guessed**. Users see a **check DrogonTV guide** qualifier because a listed channel does not establish that the stream carries that program, is available or has licensed rights.

Indexing runs off-device and publishes only encrypted `sports/state/fixtures.json`; browser rendering uses the precomputed result from the existing `/web/sports` response, without searching channels, scraping Drogon, new APIs or additional startup work. The catalogue needs an intentional manual update when the provider changes its lineup. Existing device preferences, Vela calendar feeds, notifications, free-tier constraints, offline fallback and app channels are unchanged.

## Match actions and accounts

Selecting a match type pill offers **Edit** and **Delete** (hide). Edits change local date, time and location and are stored in that device's browser; hide/restore and Reset are local too. Match cards, schedule dots, directions and sharing update without a user account or shared write. Production source fixtures are untouched; maintenance releases remain protected and separate. The event-specific RSVP list is public only for published pickup dates, without exposing a general private name catalog.

## Animation — current production experience (11.6.3)

BallerWatch uses one canonical V1/V2-style app: a two-second branded wordmark splash on a new session, followed by an optional **scroll-controlled, reversible soccer stadium scene**, then the real dashboard. There is no separate V2 app; beta is a separately cached preview of main, and the retired `/v2/` URL redirects to beta.

The visual choreography follows the captain wearing number **10**, a short-sleeved kit and armband: setup, backswing, plant, kick, curved spinning ball flight towards the upper corner, a late keeper jump and glove near-miss, a subtle net impact, and a crossfade to the dashboard. The SVG player, keeper limbs, stadium/camera layers, flash, ball and net are rendered from one pure progress-to-pose calculation and move **in reverse** when the user rewinds. No video, remote data requests, or runtime model inference are required for the introduction.

The six accompanying feature captions now reflect the current app: (1) separate **Playing / Watching** matchdays for pickup, RATS, NBA and world football; (2) RSVP lists, pending withdrawals, rain and field directions; (3) RATS standings, cross-division results and ten-game scouting/probabilities; (4) contextual BallerWatch AI; (5) personal inbox and Web Push reminders; and (6) daily Watch cards, local kickoff times, Vela TV-compatible read-only `.ics` feeds, Home Screen installation and device-local settings. The same copy is used for first paint and the running feature tour.

**Rewind resistance:** scrolling normally within dashboard cards never triggers the stadium. At the boundary above the dashboard, a light accidental upward wheel/trackpad gesture (less than about 145 px of accumulated travel) or short downward finger pull (less than about 105 px) is held at the boundary. A firmer, continuous pull passes through and reverses the intro as before. Wheel bursts reset after a short pause; touch resistance resets at the end of each gesture. Skip Intro, natural down-scrolling, dialogs, nested scrollable lists, and reduced-motion mode are not blocked. Keyboard focus, browser back/restore, offline cards and main data loading remain independent of animation.

## Rewind recovery and subscription troubleshooting (11.6.4)

The v11.6.3 resistance only ran when the cinematic canvas was mounted. The session flag for an already-watched intro instead loaded the dashboard alone, so ordinary repeat visits had **no rewind gate**. v11.6.4 keeps the fast dashboard-first load, intercepts a gentle upward pull at its top, and mounts the reversible stadium only after a continued intentional gesture. A tiny vertical elastic response makes the boundary visible. A short-lived scroll lock catches native iOS momentum crossing the boundary; it never applies to scripts that navigate the scene, nested scrollable lists, dialogs, reduced-motion views, or ordinary downward page movement. Intro Skip and offline startup remain independent.

**Calendar subscription:** BallerWatch's read-only ICS URL includes `teams`, `pickup`, and `watch` query selections. The endpoint regenerates event content against the currently indexed source each time the **same URL** is fetched, but **does not add future selections** made on an independent device. After adding NBA or football teams, copy a fresh URL from BallerWatch settings and replace the saved BallerWatch source under Vela TV's profile-scoped calendar connections. Sony and Samsung Vela clients encrypt that saved source per profile; feeds normally refresh within 15 minutes of active use. Vela's native calendar currently projects only the next seven days. The calendar's displayed refresh status can distinguish a failed fetch/cached result from a verified source; do not publish or log private subscription URLs while debugging. An opt-in stable device-specific subscription requires a separate authorized and revocable contract; it is not implemented.

## Visible dashboard resistance (11.6.5)

On desktop and iPhone, the dashboard now physically moves by up to 28 pixels while a resisted upward gesture is held at its top boundary. A small, temporary glass cue says “Pull to rewind” and shows progress; it is hidden once the gesture ends or the intro is entered. A continuous, stronger upward wheel/trackpad pull (about 210 CSS pixels of accumulated delta) or downward finger pull (about 155 CSS pixels of travel) releases the gate and rewinds into the original soccer scene. The change no longer throttles upward scrolling when already inside the scene. These thresholds are interaction heuristics, not guaranteed physical distances across devices; reduced-motion users remain in the dashboard.

## Validation

The `Validate code` workflow runs Node regression tests, version/privacy checks, Worker bundling and Chromium/WebKit browser scenarios before any beta publication. `tests/frontend/beta-channel.test.mjs` checks two-source provenance, route and PWA scope, and the browser suite covers anonymous Edit/Hide/Restore plus root/beta isolation. Browser and deploy tests are notification-silent. Production is still promoted through the reviewed release process, with Worker health checks before a Pages dispatch.

## Settings channel switching (11.2.0 beta)

Open **Settings → App channel** and choose the active environment. A non-sensitive device preference records the most recent choice. The app navigates to the other canonical URL with no private query string or fragment, and never changes the running service-worker scope in place. Production is the default when the setting is missing or invalid, and the beta availability check fails safely. The selector is now available in both environments following the manual 11.2.0 production promotion; the direct beta URL remains available.

## Soccer animation update (11.2.0 beta)

The single progress-to-pose calculation now produces separate torso, arm, planted leg, kicking calf and keeper limb transforms. A projected gravity-like quadratic flight with light curl reaches the same upper goal corner; its arc-length-based rotation, slow net arrival and restrained net deformation are reversible. No additional rendering framework, animation data polling or user-data dependency was introduced. Native scroll, reduced motion, Skip, replay function, static fallback and immediate schedule preparation remain unchanged.

The Pages workflow makes an HTTP request to the public Beta URL after deployment and checks its HTML and service-worker bytes against the validated artifact. It also confirms production HTML matches the separate `production` checkout byte-for-byte. A successful artifact upload alone is not treated as sufficient; deployment fails if the public Pages CDN never serves the intended bytes.
