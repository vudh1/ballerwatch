# BallerWatch V2 — implementation and operations

Current product release: **8.13.0**. V2 was introduced in 8.10.0. It is a separate frontend over the same backend and canonical encrypted data. V1 remains at its existing root route.

## Production routes and identities

| Experience | URL | Manifest ID / start URL / scope | Worker scope |
| --- | --- | --- | --- |
| V1 | https://vudh1.github.io/ballerwatch/ | `/ballerwatch/` | `/ballerwatch/` |
| V2 | https://vudh1.github.io/ballerwatch/v2/ | `/ballerwatch/v2/` | `/ballerwatch/v2/` |

Both are physical static directories. Direct navigation, refresh, bookmarks and shared links work on Pages without a client router. V2 has its own manifest and local 192/512px PNG install icons. Add to Home Screen from the V2 URL launches V2; V1 retains its install identity. Verify the release tag, `production` commit, Worker version and Pages asset version when diagnosing a rollout.

## Entry and card layout

The 8.13.0 sequence is **brief brand launch → scroll-controlled soccer hero → original V1 cards**. It replaces the previous always-visible background animation and the separate lime editorial layout.

- A 1.4-second BallerWatch wordmark/ball/pitch launch uses emerald, deep green and cool blue accents. It fades into the hero. A visible Skip reaches matches immediately.
- The scene owns native vertical scroll until the shot reaches the net. Reverse scrolling reproduces every pose. The cards fade in only at the final reveal, without a reload or a second data initialization.
- The main feed uses the exact V1 match, calendar and standings markup and inherited shared styles. The V2 stylesheet does not redefine those card surfaces. Settings, Inbox, the AI launcher, roster, directions, sharing and administrator dialogs keep their established controls.
- There is no sidebar, editorial card, promotional shortcut grid or bottom navigation. The compact phone header avoids overlapping the settings button.
- A collapsed **V2 experience** control below the standings contains Replay, Open V1 and V2-only frontend-cache controls.

`ballerwatch:v2:launch-seen` and `ballerwatch:v2:intro-seen` are session-only flags. The launch runs once per V2 tab/installed-app session; completing or skipping the hero makes subsequent opens in that session go straight to the cards. Replay starts the hero without replaying the splash or restarting data. No scroll progress is persisted. Neither V1 intro state nor V1 presentation preferences are changed.

Reduced motion bypasses the splash and long hero, showing the cards immediately with a short static note. Animation/script failures fail open; a 2.5-second prepaint watchdog releases the cards if the optional timeline cannot initialize. Critical data and session restoration always start independently.

## Shared architecture and privacy

Production remains dependency-free plain JavaScript. Both documents load the same `frontend/web/app.js` exactly once. `lib/client.js` is the shared API/session transport. The controller owns the existing calendar, next game, freshness, standings, scouting, roster, AI, Inbox, account/admin actions, Web Push, badges and polling.

Both use the same Cloudflare Worker endpoints and AES-GCM-encrypted canonical `runtime-state` branch. V2 creates no backend endpoint, dataset, state branch, watcher, index generation or Calendar synchronization job. Browser code never reads private runtime-state files directly. Existing backend authorization and validation still govern mutations.

Authentication/account state is shared intentionally. V2 presentation keys remain namespaced. Anonymous public calendar/standings snapshots use strictly allowlisted, date- and age-bounded device caches; private roster data and scouting responses remain in memory. Frontend workers do not intercept remote API requests or cache authenticated responses. The existing visitor name/team choices are intentionally shared across V1/V2. No additional API client or polling loop is created by the cinematic.

## Choreography and assets

`frontend/web/v2/scene-config.mjs` defines the pure `scenePose(progress)` mapping and configuration. The sticky full-screen SVG scene uses transforms and opacity, one requested frame per scroll/resize event, and no autoplay, physics engine, wheel interception or scroll trap. Application data never rerenders on animation frames.

| Progress | Action |
| --- | --- |
| 0–0.15 | Player setup and backswing |
| 0.15–0.30 | Shooting movement; contact at `SCENE.contact` |
| 0.30–0.84 | Curved ball flight, spin, scale and camera tracking |
| 0.60–0.80 | Keeper dive; narrowly missed glove |
| 0.84–0.92 | Upper-corner arrival and lightweight net pulse |
| 0.92–1.00 | Scene fades and the already-loaded V1 card feed appears |

The shooter wears **10**, attached to the moving body group. The previous underlying number-7 path is removed. Original vector stadium/crowd/lighting/field/foreground assets are local; player/ball/keeper/goal/net/impact layers have stable `scene-*` IDs in `v2/index.html`. No licensed player, club, broadcaster or game imagery is used. Install icons derive from the existing project-owned icon.

To tune the experience:

1. **Launch length:** change `SCENE.launchMs` (default `1400`).
2. **Scroll duration:** change `SCENE.scrollScreens` (default `3.2`). The hero uses that many stable `svh` screens of travel, plus its one-screen sticky stage; dashboard height cannot change the shot timing.
3. **Ball curve:** edit `SCENE.ball.start` (`477,741`), `.control` (`875,125`) and `.corner` (`1260,390`) in the 1440×900 world. Tune `contact` / `flightEnd` for flight timing.
4. **Keeper:** edit `diveStart` / `diveEnd` (`0.60` / `0.80`) and `SCENE.keeper` origin/travel/rotation. Retain the near-miss regression when changing geometry.
5. **Artwork:** replace `v2/assets/stadium.svg` or SVG layers in `v2/index.html`, retaining IDs/coordinates or updating the timeline geometry. A renamed stadium must also update `SCENE.stadiumAsset`, the SVG image reference and worker precache list.
6. **Replay:** expand **V2 experience → Replay the moment**. Reduced motion keeps the cards available and explains why the hero is paused.

The timeline pauses in the background, cancels pending frames on page exit and restores listeners on back/forward cache return. Further scrolling after progress 1 does not recompute an unchanged pose. Reverse scrolling remains available until the hero is explicitly skipped.

## iPhone and accessibility

V2 retains `viewport-fit=cover`, dark launch/theme colors, Apple standalone metadata and distinct launch scope. It uses `svh` scene sizing with a `vh` fallback and `dvh` dialog bounds. Scene controls, cards and dialogs account for top/bottom/left/right safe areas. Asymmetric landscape tests inject 59px/34px insets.

Native touch scrolling drives the scene; no global touch cancellation is added. Existing horizontal card gestures stay intact. Controls have visible focus, meaningful labels and at least 44px touch targets. Decorative SVGs are hidden from assistive technology. The real keyboard/touch Skip controls can reach the cards immediately; unrevealed cards are inert. Text inputs remain at least 16px.

The existing synthesized stadium soundtrack remains optional, gesture-gated and stored under the V2 music preference. No audio autoplays before interaction. Shared visibility handling suspends audio.

Physical iPhone Safari installation, hardware audio, real push delivery and VoiceOver remain manual hardware checks. Automated Chromium/WebKit touch, viewport, standalone, reduced-motion, portrait and landscape checks do not certify hardware behavior. Tests never send real notifications or mutate Calendar/RSVP.

## PWA caching and updates

V2 registers `v2/sw.js` at scope `./`, importing the shared `../sw.js` implementation. Experience selection derives from the registration's script URL. V1 keeps its root registration. Push icons/launch targets resolve to the installed experience.

| Cache | V1 | V2 |
| --- | --- | --- |
| 8.13.0 shell | `ballerwatch-v8-13-0-shell` | `ballerwatch-v2-v8-13-0-shell` |
| Existing derived device state | `ballerwatch-device-state-v1` | `ballerwatch-v2-device-state-v1` |

Each worker removes only its own obsolete shell caches. It leaves the other experience, device state and unrelated origin caches intact. Failed responses are not cached; missing scripts never receive HTML; navigation fallbacks use only that worker's document. The parent V1 worker cannot answer an uncontrolled V2 navigation with V1 HTML. Initial claims/scope handoffs do not reload; established later-update behavior and Worker/Pages readiness checks remain in place.

Offline startup provides cached UI and a valid previously saved public schedule/standings when available. Cold offline startup has a usable empty/reconnecting state; private operations require connectivity.

**Clear V2 frontend files only:** expand **V2 experience → Offline storage → Clear V2 frontend cache**. It deletes only names matching `^ballerwatch-v2-.*-shell$`, preserving V1, authentication, device preferences/notifications and backend state. Reconnect before relying on the next offline startup. Do not clear all site data or unregister the root worker.

From repository root:

```bash
node --test

node scripts/privacy-audit.mjs

node scripts/build-web.mjs
node tests/frontend/live-readonly-smoke.mjs
```

CI also syntax-checks every JS/MJS file and Apps Script, and dry-bundles the Worker with pinned `wrangler@4.145.0`. Browser tests install test-only `playwright@1.56.1` outside the repository and run Chromium plus WebKit on the packaged HTTPS source at the real Pages base path. The restricted local runner may use `BALLERWATCH_CHROMIUM_SHELL=1`, mocking only its unavailable native badge bridge; CI uses full unmodified Chromium/WebKit.

Browser coverage includes launch timing, critical reads during the hero, exact reverse poses, goal reveal, computed V1/V2 card appearance equality, touch/Skip/replay, refresh, iPhone safe areas and header bounds, reduced motion/standalone, asset/script failures, visitor settings, authenticated synthetic session restoration/rosters, optional failures, V1 storage sentinels, both worker scopes and offline routes, and V2-only cache clearing. No live account mutations are used.

Release flow: dedicated branch → green **Validate code** → PR → checked squash merge → **Promote production release** → matching Release/`production` → **Deploy BallerWatch Worker** encryption audit/live readiness → **Deploy GitHub Pages app**. `.github/workflows/complete-8-13-0.yml` follows the existing version-pinned handoff pattern and runs read-only production API smoke checks before dispatching the established promotion workflow. It cannot deploy independently or bypass validation.

## Rollback

Use a new forward fix/release commit and the normal validated promotion flow. Do not reset or force-push production.

To roll back only V2, restore `frontend/web/v2/` from a known-good V2 commit, retain current V1/shared contracts, bump the PATCH and shell asset versions, validate both experiences and promote. Keep the V2 manifest/start URL/narrow worker available so an installed V2 never silently becomes V1. Verify every precache entry. Never reset, fork or copy canonical runtime-state as part of rollback.
